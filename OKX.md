# OKX U.S. spot execution

KAIROS supports separate OKX U.S. hosted-demo and real-money cash-spot environments. Both start paused and unarmed. Installing credentials or enabling a server gate does not authorize a trade.

Offline fixtures are not OKX executions. Existing hosted-demo cycle and TWAP evidence does not verify the strategy integrations below, establish profitability, or qualify live trading. Each strategy test needs its own finite demo authorization. Nothing here qualifies, changes or starts the frozen Alpaca trial.

## Private setup

1. In the official OKX interface, choose **Trade → Demo Trading → Personal Center → Demo Trading API → Create Demo Trading API Key**. Use a dedicated account context without another order manager. Grant Read and Trade, not Withdraw. Restrict the key to the server's IP where supported. Trade permission alone is not an endpoint restriction; KAIROS separately prohibits transfers, withdrawals, borrowing and account-setting writes.
2. Inspect **Demo Trading → Assets** for the virtual funds supplied by OKX. Choose an actual funded spending currency. Follow the [official demo guide](https://www.okx.com/en-us/help/how-to-use-demo-trading) if initial virtual funds are unavailable, before binding an account to KAIROS. Do not reset a bound account or adjust its virtual balance to make a failed run pass. KAIROS has no funding/reset API.
3. Configure cash-spot availability in OKX itself. KAIROS rejects unsupported account modes, borrowing settings/liabilities and conflicting working orders. Pre-existing virtual coins remain unallocated; they need not be sold to begin.
4. Install the credentials privately using the service's environment configuration. Never paste keys or passphrases into chat, logs or the dashboard. The names in [.env.example](.env.example) are exact:

| Environment | Credentials | Required write gates |
| --- | --- | --- |
| Hosted demo | `OKX_DEMO_API_KEY`, `OKX_DEMO_SECRET_KEY`, `OKX_DEMO_PASSPHRASE` | `ALLOW_OKX_DEMO_TRADING=true` |
| Real money | `OKX_API_KEY`, `OKX_SECRET_KEY`, `OKX_PASSPHRASE` | Both `ALLOW_OKX_TRADING=true` and `ALLOW_LIVE_TRADING=true` |

All gates default to `false`. The existing `OKX_*` credential names are live credentials, never demo fallbacks. Alpaca remains paper-only. No key, passphrase or signature is returned to the browser.

Restart the service safely after changing its environment. Missing OKX keys do not prevent Kraken or Alpaca startup. `KAIROS_EXCHANGE` accepts `kraken`, `alpaca`, `okx-demo` and `okx` for a new installation. The saved dashboard selection takes precedence; changing this variable cannot bypass an existing non-flat venue.

## Environment and instrument identity

| Service | Hosted demo | Real money |
| --- | --- | --- |
| REST | `https://us.okx.com` | `https://us.okx.com` |
| REST environment header | `x-simulated-trading: 1` | `x-simulated-trading: 0` |
| Public WebSocket | `wss://wsuspap.okx.com:8443/ws/v5/public` | `wss://wsus.okx.com:8443/ws/v5/public` |
| Documented private WebSocket | `wss://wsuspap.okx.com:8443/ws/v5/private` | `wss://wsus.okx.com:8443/ws/v5/private` |

This implementation uses public `books5` full snapshots and authenticated REST order/fill reconciliation, not private-stream execution messages or a reconstructed incremental book. Business WebSockets are not needed. Credentials are not forwarded through redirects. There is no global-host, live/demo, other-venue or credential fallback.

Discovery uses the authenticated account's enabled SPOT instruments and `tradeQuoteCcyList`. A selection such as `okx-demo:BTC-USD:USDC` means native instrument `BTC-USD`, settled in **USDC**. It does not mean USD cash. USD, USDC, USDG and USDT are separate assets. An unavailable variant is rejected rather than replaced.

Only explicitly selected execution markets receive book subscriptions: at most ten for demo strategies, one for live execution. Browsing charts/favorites does not retarget execution. Charts read up to 300 native candles from the U.S. REST endpoint with the selected environment header. They preserve source opening times, base-asset volume and the forming/completed marker; daily bars open at UTC midnight. Missing bars are not invented. Chart responses never supply execution prices or strategy history. Demo strategies make separate native history reads, described below. Market-list turnover and percentage-change data remain unavailable; no chart data comes from another venue or environment. Both venue timestamps and local receipt times remain visible. Reconnection invalidates old books; heartbeats do not freshen prices. Book reads wait at most ten seconds, and the feed allows five connection attempts before requiring an explicit restart.

OKX's `maxLmtAmt` is a USD-denominated exchange limit even for a USDT-priced order. KAIROS checks it with a fresh same-environment native quote/USD index, such as `USDT-USD`, rather than assuming stablecoins equal USD. The preview shows that reference and the estimated USD notional; each actual order records a new check, with freshness checked again after transport admission. Missing, mismatched or stale references block submission. Preflight and execution preparation can wait up to 75 seconds for a fresh reference, polling public reads once per second. Stop cancels the wait, including an in-flight read. The wait does not extend finite permission or begin/repeat an order intent. The preview waits after account checks, immediately before pricing from a fresh book. Execution also waits after its account checks and refreshes any account proof that expires during a long wait; the same permission and TWAP slot deadlines bound those reads. Fresh books and risk checks still gate submission. A short-lived, same-environment cache retains the original source timestamp; neither receipt nor reuse freshens it. The ten-second freshness gate remains unchanged, and expiry after an intent is created blocks that intent rather than retrying it. This reference only checks the venue cap: it does not convert funds, supply execution prices or change the ledger's spending currency. Native USD-priced books need no FX reference, regardless of their settlement currency.

## Execution cycle

1. Stop and reconcile the current venue. It must have no working/uncertain orders, unresolved recovery or owned non-cash holdings. Select **OKX Demo — virtual funds**. The destination remains unarmed. The separate **OKX Live — real funds** selection cannot inherit demo authorization.
2. Use **Exchange accounts → OKX** to inspect native balances without allocating them. Open **Execution cycle…** in the settings controls.
3. Choose the exact instrument/currency. Prefer an enabled BTC market with adequate visible liquidity. Set the initial allocation, entry budget, absolute buy ceiling/sell floor if desired, exit-attempt limit and duration. The initial defaults are a 500-unit allocation, 25-unit order cap, 100-unit exposure cap and 12.50-unit daily-loss limit, denominated in the selected currency, not assumed dollars. These values do not fund the account.
4. Click **Run read-only preflight / preview**. This saves the explicit execution-market selection and reads broker evidence; it sends no order and does not establish an allocation binding. It checks identity, permissions, available funds, native rules, planning fees, clock, book age/spread, size and visible liquidity. If the budget cannot leave a sellable quantity after fee/lot allowances, it shows the minimum required amount and submits nothing.
5. Review the masked account, actual currency, budget/quantity, fee source, absolute and slippage bounds, attempt counts, duration and dust policy. A cycle permits one entry attempt and one to three explicitly selected exit attempts; duration is 30–900 seconds. The preview expires after two minutes. Changes or Stop invalidate permission.
6. Type the exact confirmation shown in the preview, then click **Authorize this finite run**. Demo cycles use `AUTHORIZE OKX DEMO EXECUTION_CYCLE`. Live cycles require `AUTHORIZE OKX LIVE REAL MONEY EXECUTION_CYCLE` and both live gates. These are separate permissions, not interchangeable confirmations.
7. Inspect **OKX finite-run evidence**, Orders and Portfolio. The buy uses a bounded cash IOC limit order. Only terminal execution evidence establishes acquired ownership. The sell uses fresh native data and the quantity actually acquired after fees/rounding. The engine reconciles executions and balances, then stops. No model, profitability threshold or passive maker fill controls this diagnostic.

When account fee discovery is unavailable, only a demo execution cycle can use a positive, explicitly supplied **Demo-only fallback planning allowance · bps**. The preview names that limitation and allowance. It is not an actual fee, cannot be used for live trading or TWAP, and cannot replace missing execution-fee evidence.

The command flow is `POST /api/okx-preview` followed by `POST /api/okx-authorize`. The latter accepts exactly `preview_id` and `confirmation`; it cannot increase approved terms. Both retain normal Origin, JSON and CSRF checks. Use the dashboard rather than putting credentials or CSRF tokens in shell history.

## Outcomes and recovery

| Result | Meaning |
| --- | --- |
| Not run / authorization required | No finite permission has been issued. |
| Preflight blocked / `PREFLIGHT_BLOCKED` | A required check failed. Inspect the exact check and corrective action; a preview failure authorizes nothing. |
| `NO_FILL` | The entry was terminal without execution; no sell follows. |
| `STOPPED` | An active TWAP or demo strategy was explicitly stopped with resolved orders/accounting. Actual fills, fees and retained holdings are recorded; this is not schedule completion or liquidation. |
| `PARTIAL` | Some execution occurred, an exit was blocked, Stop interrupted the run, sellable inventory remains, or an operational budget bound failed. |
| `UNKNOWN` | Submission outcome is unresolved. Reconcile the original client intent; never repeat it blindly. |
| `RECONCILIATION_PENDING` | Execution/accounting evidence is incomplete or inconsistent. No accounting success is claimed. |
| `PASSED` | Positive buy and sell executions, no unresolved orders, matched accounting and no cycle residual. |
| `PASSED_WITH_DUST` | The same execution/accounting checks passed, but explicitly recorded unsellable inventory remains. This is not complete liquidation. |

The report retains client and broker IDs, native executions, fees by currency, exact residual, optional fresh-book value estimate, closing ledger and reconciliation evidence. `submitted` is true for established broker submission/rejection, false when nothing was sent, or `unknown` when delivery cannot be established. A value estimate is not a fill or a currency conversion.

Planning fees reserve capacity; they cannot guarantee the exchange's eventual charges. An actual quote-fee overrun remains recorded and prevents a passed result if entry debit exceeds the approved budget. The already-authorized owned exit can still reduce exposure; no extra purchase is permitted. Actual signed fill fees/rebates determine accounting: negative native fees are charges, positive values are rebates. Base fees reduce acquired inventory; quote fees affect that exact quote asset. Unexpected third-currency effects remain recorded and block further trading instead of being guessed, converted or silently taken from unrelated holdings.

The bot ledger is an explicit allocation, not the total account balance. Account baseline comparisons include pre-existing assets without importing them into bot ownership or profit. Native order observations and executions are deduplicated; cumulative quantities never manufacture fills. Temporary order/fill and balance lag has bounded read-only reconciliation. An IOC can wait up to 45 seconds for execution/fee evidence; settlement reads also have a 45-second bound. A missing response, timeout or restart never permits resubmission.

For an accounting investigation, open **Exchange accounts**, select **OKX transaction bills**, and click **Refresh**. This read-only view uses the existing account binding and shows the native bill currency, balance change, balance after the event, signed fee, and order/trade identifiers. Values retain their original strings; missing fields are shown as `—`, never zero. Baseline and unrecognized activity remain visible and are not adopted. The API also returns the binding baseline and reported balance snapshot for comparison. Reads use the existing pagination guards and 30-second account-view cache. Viewing bills does not reconcile, approve qualification, alter the ledger, or grant trading permission.

Demo reconciliation can distinguish the observed account-summary representation from exact native accounting. This path requires every new bill to match an owned terminal fill, both currency legs, actual signed fees, native IDs/timestamps and every running balance checkpoint. Bill totals must equal the exact ledger, and two independent uncached reads must agree on identity, history, bills and balances. An affected currency must be unfrozen and fully available. Only the exact shortest decimal representation of the expected normal binary64 value is accepted—not a configurable epsilon or a general rounding tolerance. The model uses integer and Decimal arithmetic; it is an observed demo reporting model, not an OKX precision guarantee. Live reconciliation stays exact. Missing/revised bills, foreign activity, unresolved orders and unexplained differences remain blocking.

The latest reconciliation retains the raw bill checkpoints, expected/reported values, exact representation difference, read times and original pending clock. No balance, fee or dust adjustment is booked. **OKX finite-run evidence** shows `original_run` and `latest_account_reconciliation` separately: a later read-only match does not rewrite the original outcome or grant another trading permission. It also shows `latest_run_execution`, derived from saved orders belonging to that exact authorization, and `current_owned_balances`. This exposes actual submissions, fills and fees even when an older Stop/restart summary was incomplete. Reading this evidence never rewrites the original report or adopts unrelated orders.

**Stop** revokes permission immediately. It attempts cancellation only for known owned working orders, reconciles cancellation/fill races and retains holdings. After those reads, an active TWAP or demo strategy receives a final `STOPPED` report with actual orders, fills, fees, remaining inventory and reconciliation. Unknown submissions remain `UNKNOWN`; unresolved orders or incomplete Stop reads remain `RECONCILIATION_PENDING` and blocking. Repeated Stop or restart does not overwrite an already-final report or resume the schedule. Cancellation acceptance is not terminal cancellation. Rejected or uncertain cancellation intents are not blindly replayed. An unresolved cancellation may require operator investigation at OKX. Stop's final settlement wait is bounded to ten seconds. A daily-loss halt is not a guaranteed maximum loss or surprise liquidation.

**Reconcile** performs broker reads and applies verified native evidence. It does not trade, acknowledge external orders, adjust balances or rearm. **Restart engine** restarts data services and reconciliation and attempts cancellation of previously owned working orders. It never submits another entry or exit; another finite preview/confirmation is required to trade. Interrupted runs remain interrupted even if later reads resolve their orders. Shutdown and process restart preserve intents and revoke permission.

State lives in `DATA_DIR/okx-demo.sqlite3` and `DATA_DIR/okx-live.sqlite3`, separate from Kraken and Alpaca. Bindings use native account identity, venue and environment. Rotating a key for the same account preserves state; a different account cannot inherit its ledger. Do not remove a store to evade recovery. Back up the databases with the same SQLite/WAL precautions as other venues.

External activity after binding, changed account identity, unexplained balances, missing fees and unresolved orders block new execution. Even disclosed dust remains an owned holding under the existing flat-before-switch rule. Do not erase it or buy extra coins to conceal it.

## Finite TWAP

Save **TWAP** settings for the selected native instrument: side, base quantity, explicit parent limit, at least two slices and duration. The initial parent limit `1` is deliberately inert, not a market-price suggestion. Preview rejects a currently nonmarketable parent limit. Choose a duration that leaves room for account reads and the engine interval; missed slots are not replayed.

Click **Preview TWAP…**, or choose **Finite TWAP** in the execution dialog, then review and type its separate confirmation. The demo phrase is `AUTHORIZE OKX DEMO TWAP`; live uses `AUTHORIZE OKX LIVE REAL MONEY TWAP`. Approval uses the existing `programs.prepare/run` scheduler, normal risk checks, durable intents and native accounting. Sell programs require already allocated, available inventory. They cannot sell unrelated demo holdings.

A passing preview checks the price now; it does not reserve that price until authorization or later windows. The preview shows the bid, ask, fixed parent limit, remaining price room in basis points and original quote timestamps. Account checks and market movement can leave that limit unmarketable by the first or a later window. An unmarketable parent limit at the scheduled check skips that window; a failed later execution check stops the run. Neither lowers a sell floor, raises a buy ceiling or retries automatically. New price-blocked Activity records retain the contemporaneous bid, ask, limit and quote timestamps; historical missing prices are not reconstructed.

Each TWAP slice's final IOC price is calculated from a fresh same-environment book after account, cap-reference and venue-band reads. It uses the existing tick-rounded slippage policy within the authorized parent limit; quantity and submission count do not increase. The updated price must pass the finite budget, available-funds, native-band, size, allocation, exposure and final fresh-book checks before a durable intent is saved. Stop and slot/permission deadlines still apply. A later price move can still block submission; the engine does not loop to chase prices, amend a saved intent or replay a failed slice. Execution-cycle pricing is unchanged.

Completion stops and clears permission. The dashboard separates orders with actual fills from processed windows, recorded skipped checks and elapsed missed windows. Finished schedules say **no fills**, **partial fills**, **filled** or **unresolved**, based on the saved order evidence and original program terms. Existing Activity supplies legacy skip evidence without rewriting old records. New finite-run reports retain the execution summary as well as schedule status. `TWAP_COMPLETE` describes a completed schedule, not guaranteed full fills, flatness, round-trip qualification or profitability. A completed/changed schedule requires explicit **New strategy run…** before another preview. Every hosted TWAP run requires its own authorization; cycle consent does not authorize an additional experiment.

Live predictive strategies, live DCA/rebalancing, margin, derivatives, transfers, withdrawals, automatic funding, compounding and local OKX fill simulation remain unavailable. Kraken and Alpaca retain their own strategies and recovery rules.

## Bounded demo strategies

The separate protocol `okx-demo-bounded-strategies-v1` connects the existing HTF, maker, scalping, arbitrage, DCA and rebalance logic to native demo execution. TWAP keeps its existing authorization above. These are experimental test paths, not profitability recommendations.

1. Select **OKX Demo**, save the strategy and its settings, then click **Preview strategy…**. Use exact account-enabled market identifiers in a rebalance basket, including its primary market and `CASH`. Arbitrage uses the existing bounded BTC/ETH triangle search; absent native cross markets are blockers, not permission to substitute another venue.
2. Set a starting-currency buy budget, duration of 30–86400 seconds and 1–100 total order attempts. DCA's complete schedule and prefunding must fit those limits. Rebalancing performs at most one settled order per saved cooldown. Scheduled children refresh their price once after slow account/reference reads, within the unchanged authorization and DCA-slot budget, without increasing quantity. No missed window is replayed.
3. Inspect **every market** in the preview. After history and reference reads, the preview captures all required books and checks that the entire set is still fresh before deriving terms. Each market has its own native quote, cumulative buy budget, fee allowance and absolute price bounds. Starting-currency buy commitments are also capped across markets. For unspecified bounds, the preview proposes a tick-rounded ceiling 5% above the current ask and floor 5% below the bid; confirmation approves those displayed absolute numbers, not a moving band. Existing per-order, spread, slippage, exposure and daily-loss checks still apply. Market quantities and currencies are never added at assumed parity.
4. Read the opening owned balances and execution policy. Confirm only with `AUTHORIZE OKX DEMO STRATEGY`. This one-use preview expires after two minutes; settings changes, Stop and restart invalidate it. A fee increase or changed market rule requires a new preview.

All strategy markets must use their native price currency. A USD-priced instrument settled in a different stablecoin remains eligible only for the existing cycle/TWAP paths; strategy cost and history checks do not assume the currencies are equal. Additional account balances remain outside the bot allocation.

HTF requires 30 adjacent, confirmed native bars. Scalping requires its completed native one-minute window. Reads use OKX's `confirm=1` marker and UTC-aligned intervals; gaps, malformed bars and false completion are blockers. VWAP and trade counts are unavailable on this endpoint; shared history rows use the existing zero-as-unavailable convention for those two unused signal fields. OHLC and base volume stay native. There is no minute synthesis, chart fallback or startup/outage catch-up. `multibar-v2` uses the existing deterministic signal and candidate lifecycle, but its run deadline is this demo authorization—not the frozen Alpaca trial. Legacy HTF, maker and arbitrage still require Jev; missing model/data requirements block orders.

Before HTF evaluates a tick, its initial book check can recover from a ten-second books5 read timeout. The whole check is bounded to 60 seconds and the original authorization deadline, with Stop checked during the wait. This applies only to an active, reconciled demo run without unresolved orders. It does not restart an exhausted feed, accept stale books or retry strategy evaluation. The dashboard reports the wait; no new orders or protective exits run without fresh data. Recovery retires old entry candidates and establishes a fresh entry baseline, preserving existing exit plans, inventory, budgets, attempt counts and deadlines. Book failures later in evaluation or execution, invalid books and order/accounting uncertainty still stop the run. Exhausted recovery stops it too; later fresh data or a restart cannot reopen that authorization.

After the initial book check, demo HTF refreshes authenticated fees before evaluation. A 30-second grace covers that read, retries of transient fee-GET failures, and a final fresh-book check; it does not restart the 60-second book wait. The dashboard shows fee recovery when fresh fees are unavailable. No strategy evaluation, new orders or protective exits run during the grace. Both original authorization clocks and Stop still apply. Fee data must remain less than 60 seconds old, books must pass the unchanged freshness checks, and refreshed fees cannot exceed the authorized allowance. Recovery retires outage-era entry candidates without changing holdings or exit plans. Invalid fees, credential failures, higher fees, exhausted grace and fee failures later in evaluation/execution still stop the run. Other strategies and exchanges do not inherit this recovery path.

HTF entries and maker quotes use native `post_only`, without taker fallback. Other orders use IOC. Only one order may remain unresolved. Post-only orders have **no exchange-side expiry in this implementation**: the engine observes them for at most 30 seconds or the earlier review/run deadline, then cancels the owned remainder and reconciles native evidence. Network and scheduler latency add delay. During a process or network outage, the order can remain open at OKX; Stop/restart attempts owned-order cancellation when connectivity returns. Cancellation acceptance alone is not completion.

Base-denominated execution fees reduce HTF/scalp ownership and intermediate arbitrage proceeds exactly once. HTF/scalp quarantine unrelated opening inventory rather than adopting it into a new position. Retained strategy positions prevent changing strategy or market. Arbitrage is three sequential orders, never atomic: a partial leg stops the route and leaves its intermediate inventory and original cycle record for investigation. No automatic rollback or cleanup trade follows. After native reconciliation, **Reconcile** can explicitly acknowledge that interrupted route: its original plan, report and retained ledger are archived, the recovery latch clears, and trading stays unarmed. This cannot adopt external orders, change balances or replay a leg.

Stop, expiry, a completed schedule or the attempt cap ends permission. `STRATEGY_COMPLETE` means only that a finite bound ended the run; it does not mean a filled schedule, closed position or profitable strategy. Fixed price bounds and exhausted permission also constrain protective exits. Holdings and dust may remain without active protection after the run stops. Never rely on a local stop or test deadline as a guaranteed liquidation. Reports retain original orders, native fees, all closing currency balances and reconciliation evidence.

## Verification

Offline tests cover native routing/signatures, prohibited writes, account/currency isolation, fee signs, durable unknown outcomes, duplicate/late observations, partial/no fills, cancellation/fill races, restart, balance lag, finite cycle/TWAP paths and dashboard consent. Browser checks use deterministic native REST fixtures, not an authenticated OKX account.

Authenticated hosted-demo evidence now includes a filled buy/sell cycle with final bill-backed accounting reconciled afterward and dust retained. A separately authorized two-slice TWAP buy filled both slices. Subsequent sell schedules produced a partial sale and price-blocked windows; schedule completion did not mean liquidation. These observations establish neither guaranteed fills nor profitability. Live execution remains unverified. Credentials, previews and prior consumed permissions never authorize another run; inspect fresh finite terms and authorize each new demo or live run separately.

Documentation examples and mocked results do not establish account capability or execution.
