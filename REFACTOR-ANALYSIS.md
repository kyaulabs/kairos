# Settings and redundancy analysis

Reviewed the application at `4b48971`, before editing: every first-party Python module and dashboard JavaScript module, the settings markup, deployment examples, environment example, persistence/API call paths, and relevant regression tests. No production database or `.env` was read. Vendor code and supplied brand files are outside this refactor.

| Finding | Consequence | Refactor |
| --- | --- | --- |
| `asset-class` and `product` both write `settings.product` in `app.js`. The first is not an independent asset-class setting. | Two controls can override one choice; changing Asset class can replace Margin with Spot. | Keep Product as the only execution-product selector. Unsupported instruments remain visible in market browsing. |
| `full-allocation` writes `order_size`, `max_exposure` and `reinvest_profits`. | A second editor changes three risk settings, including a checkbox the operator may not intend to change. | Remove the shortcut. Edit each cap and reinvestment once in Capital. Preserve existing saved values and defaults. |
| Futures collateral/leverage live in Strategy; spot allocation lives in Capital; paper-margin leverage lives in Execution. Strategy-only and product-only controls remain visible outside their context. | Similar controls appear interchangeable, and inactive values can distract from the limits that actually apply. | Put allocations, risk caps and product-specific leverage in Capital. Put DCA/TWAP fields with their strategy and margin cost assumptions in Execution. Show applicable controls without copying values between products. |
| Defaults, numeric bounds, integer/boolean parsing, strategy choices and candle choices are repeated in Python, HTML and JavaScript. Several HTML inputs omit backend upper bounds. | Validation and available choices can drift. A new field needs synchronized hand edits in several lists. | Define the bot-settings contract once in Python and expose public metadata through a read-only endpoint. Use it for validation, restricted migration, select choices, form bounds, typing and applicability. Keep explicit cross-field and execution checks on the server. |
| Spot and Futures directional planners repeat maker/taker price calculations; other taker planners repeat the same slippage rounding. | Equivalent pricing rules can diverge when maintained separately. | Share pure price calculation, retaining each caller's parent-price bounds, fee reserve, depth checks and submission-time validation. |
| Three valuation paths repeat UTC-day baselining and display bookkeeping. Spot buy planning values the same portfolio twice without intervening I/O or state changes. | Duplicated bookkeeping and an unnecessary valuation request. | Share valuation recording with explicit existing portfolio keys; remove only the adjacent redundant valuation. Keep post-I/O and submission-time rechecks. |
| Futures live-position detection is repeated despite an existing helper; spot sell-funding requirements are constructed and immediately replaced. Jev's default model is repeated in entry points. | Unnecessary maintenance paths. | Reuse the existing position helper, build spot funding requirements once, and use one model default. |

The following similarities are intentional and must not be collapsed:

- Chart market/interval and bot market/HTF interval are independent. Browsing must never configure trading.
- An allocation funds a portfolio; an order cap limits one order; an exposure cap limits holdings. A DCA budget, TWAP parent cap and rebalance turnover cap constrain a run or day. None replaces the others.
- Spot, paper-margin and Futures ledgers represent different products. Spot and Futures live allocations remain separate; paper reset never alters live funds. Their leverage and fee assumptions are not interchangeable.
- Server write flags grant permission; the execution-mode confirmation arms a product; Start begins execution. They are separate safeguards, not redundant settings.
- Freshness is checked both when accepting data and before execution. Read-only display caches must not become trading inputs.
- Spot and Futures transports have different authentication, endpoints, rejection semantics and recovery. Their signed requests and accounting stay separate. Read-only account views retain their smaller allowlist.
- Browser appearance/favorites are local preferences, not saved bot settings. Environment variables hold runtime credentials and permissions, not a second trading configuration.
- The process lock is used independently by the service and smoke command to prevent concurrent ownership. This refactor does not change deployment, nonce ownership or lock behavior.

Saved field names, values, ledger keys and durable program configurations remain unchanged. Migration may supply only already-introduced program/Futures defaults; a missing legacy risk field still prevents startup. Hidden inactive fields retain their saved values. Unsupported combinations remain server-rejected; hiding controls does not grant execution permission. Spot-only capital recovery must be explicitly switched off before changing to another product.

Verification passed locally: 160 Python tests and 39 JavaScript tests, including schema/API/form agreement, inactive-value preservation, blank unconfigured TWAP limits, pricing bounds, UTC-day rollover and portfolio isolation. A differential check against the pre-refactor validator returned identical defaults and acceptance/normalization results for 19,350 settings cases. Isolated Chromium exercised Save/Start/Stop for all 12 supported product/strategy combinations, native bound validation, draft preservation during state updates, chart isolation and running-state locks. All three settings tabs fit six viewports from 1440×900 to 360×640 without page overflow. No real exchange writes, private-account probes, model calls or production restart were performed.
